# 코딩 가이드

h-port의 공통 원칙을 Python DDD 학습 프로젝트에 맞게 적용한다.

## 구조와 설계

- 업무 영역은 `app/domains/orders/`처럼 `domains/` 아래에 모으고 각 영역 안에서 `domain`, `application`, `infrastructure`, `presentation`을 나눈다. 공통 코드는 `shared/`, 의존성 조립은 `bootstrap/`에 둔다.
- 공통 요청 경계(`bootstrap/container.py`)에서 AsyncSession과 트랜잭션을 열고, 요청 정상 종료 시 응답 전송 전에 한 번 자동 커밋하며 예외 시 롤백한다. 컨테이너는 같은 세션을 모든 Repository에 주입한다. Application은 Repository로 업무만 수행하고 Session을 인자로 받거나 begin·commit·rollback하지 않는다. Repository는 SQL 실행과 필요한 flush만 한다. CLI·배치는 실행 진입점에서 같은 역할의 경계를 연다. 유스케이스마다 트랜잭션을 중첩하거나 별도 자동 전파 라이브러리·UoW를 구현하지 않는다.
- 도메인 용어를 코드 이름에 반영하고, 업무 규칙은 도메인 모델에 둔다.
- 엔티티는 식별성과 생명주기를, 값 객체는 값의 동등성과 불변성을 기준으로 구분한다.
- 애그리거트 내부의 일관성은 루트의 동작으로 지킨다. 외부에서 필드를 임의로 바꿔 규칙을 우회하지 않는다.
- 애플리케이션 계층은 유스케이스의 순서를 조율하고, 저장소·웹 프레임워크·외부 I/O는 도메인 모델과 분리한다.
- 리포지토리는 필요한 애그리거트의 저장·조회 경계를 표현한다. 모든 클래스에 인터페이스와 구현체를 만들지 않는다.
- 각 application 유스케이스 파일에 Pydantic Command 또는 Query와 일반 함수를 함께 둔다. 함수는 입력 모델과 Repository를 인자로 받으며, 별도 Handler 클래스나 Handler 생성 함수를 만들지 않는다.
- 변경·조회 유스케이스 함수는 같은 Repository 계약을 사용한다. 조회 함수는 도메인 객체를 반환하며, API 응답 스키마와 변환은 presentation의 해당 엔드포인트에 둔다. application은 유스케이스 조율·저장소 호출·트랜잭션 처리를 담당하고, 계산과 상태 변경 규칙은 도메인 메서드에 둔다. 도메인은 application이나 presentation을 import하지 않는다.
- 학습할 업무 규칙에 필요한 구조만 만든다. CQRS·이벤트 소싱·메시지 브로커는 요구가 생길 때 도입한다.
- 변경은 작게 유지한다. 버그 수정과 구조 개편을 섞지 않고, 리팩터링은 기존 동작을 보존한다.

## 컨벤션 기준과 자동 검사

- 기본 스타일은 [PEP 8](https://peps.python.org/pep-0008/)을 따른다. 외부 오픈소스에 기여할 때는 해당 저장소의 기여 가이드와 도구 설정을 우선한다.
- 이 프로젝트의 들여쓰기·인코딩·줄바꿈·Python 줄 길이는 루트 [.editorconfig](../../.editorconfig)를 기준으로 한다. Python 줄 길이는 88자로, PEP 8의 기본 권장값인 79자 대신 사용하는 프로젝트 규칙이다.
- 포맷·린트는 Ruff를 우선하고, 타입 검사가 필요하면 mypy 또는 Pyright 중 하나를 사용한다. 도구 설정은 가능한 한 `pyproject.toml`에 모으고 줄 길이를 `.editorconfig`와 일치시킨다. 도입·실행 규칙은 [빌드·문서 규칙](operations.md)을 따른다.
- 자동 검사 가능한 규칙은 도구 설정으로 관리하고, 이 가이드에는 도메인 설계·이름의 의미·예외 처리처럼 판단이 필요한 규칙을 기록한다. 린트 규칙은 기본 검사에서 시작해 필요한 것만 추가하며 모든 규칙을 일괄 활성화하지 않는다.
- 검사 도구를 도입하면 로컬과 CI에서 같은 설정으로 검사한다. 기여 가이드(`CONTRIBUTING.md`)를 만들 때는 실제 검증한 검사 명령과 이 가이드 링크를 기록한다.

## Python 코드

- 프로젝트에 설정된 Python 버전과 포맷터를 따른다. 설정이 없으면 도구나 버전을 임의로 확정하지 않는다.
- 함수·변수·모듈은 `snake_case`, 클래스는 `PascalCase`, 상수는 `UPPER_SNAKE_CASE`로 이름 짓는다. 내부용 멤버는 `_` 접두사로 표시하되 접근 제한이 강제된다고 가정하지 않는다.
- import는 파일 상단에서 표준 라이브러리·외부 패키지·프로젝트 모듈 순으로 묶고 그룹 사이에 빈 줄을 둔다. 와일드카드 import는 사용하지 않는다.
- 공개 함수와 도메인 모델에는 의미 있는 타입 힌트를 쓴다. 타입 힌트를 런타임 입력 검증으로 간주하지 않는다.
- 데이터 검증이 필요한 값 객체는 Pydantic의 `BaseModel`과 `ConfigDict(frozen=True)`로 표현한다. 엔티티의 상태 변경은 업무 의미를 가진 메서드로 표현한다.
- `frozen=True`는 내부 컬렉션까지 불변으로 만들지 않는다. 불변 값 객체의 구성 요소도 불변으로 유지한다.
- 컬렉션은 업무 규칙이 있을 때만 별도 객체로 감싼다. 가변 기본 인자를 사용하지 않는다.
- 값의 부재를 허용하면 반환 타입에 명시하고, 호출자가 부재와 실패를 처리하게 한다.
- `None` 비교는 `is None` 또는 `is not None`을 사용한다. 빈 값과 부재를 구분해야 할 때는 truthiness 검사로 합치지 않는다.
- 단순 조회는 속성으로 표현하고 형식적인 getter/setter를 만들지 않는다. 계산된 조회에는 필요하면 `@property`를 쓰고, 상태 변경은 `confirm()` 같은 업무 동작으로 표현한다.
- 간단한 변환·필터는 컴프리헨션으로, 복잡한 분기·부수효과는 일반 반복문으로 표현한다. 재할당과 반복문을 일괄 금지하지 않는다.

## FastAPI와 Pydantic

- Pydantic v2를 사용한다. API 요청·응답과 애플리케이션 계층의 데이터 전달 모델은 `BaseModel`로 정의하고, API 스키마와 도메인 모델은 역할에 맞게 분리한다.
- 길이·범위 같은 제약은 `Field`로, 추가 필드 검증은 `field_validator`로, 필드 간 검증은 `model_validator`로 표현한다. 검증기에서 DB 조회나 외부 I/O를 수행하지 않는다.
- Pydantic 검증은 데이터 형태와 값의 제약을 담당한다. 현재 상태에 따른 업무 규칙과 상태 전이는 도메인 모델의 메서드에서 지킨다. 생성 시 검증만으로 이후의 상태 변경도 안전하다고 가정하지 않는다.
- 타입 변환 허용 여부는 입력 계약에 맞춰 정한다. 자동 변환을 허용하지 않는 필드에는 strict 검증을 사용한다. 외부 입력에 `model_construct()`를 사용하거나, `model_copy(update=...)`가 변경 값을 검증한다고 가정하지 않는다.
- 검증·직렬화는 v2 API인 `model_validate()`, `model_dump()`, `model_dump_json()`을 사용한다. v1의 `parse_obj()`, `.dict()`, `.json()` 사용법과 섞지 않는다.
- 응답 스키마에는 외부에 공개할 필드만 정의하고 FastAPI의 `response_model` 또는 응답 타입으로 명시한다. 환경변수 설정이 필요하면 `pydantic-settings`의 `BaseSettings`를 사용한다.

## 검증과 예외

- 외부 입력은 경계에서 검증하고, 도메인 불변 조건은 모델 생성·변경 시 지킨다.
- 예외를 삼키거나 실패를 정상 결과로 위장하지 않는다. 외부 I/O 실패는 호출자가 대응할 수 있도록 경계에서 변환하거나 전달한다.
- 파일·연결 등 자원은 컨텍스트 매니저 또는 finally로 정리한다.
- 외부에 효과가 발생한 뒤에는 무조건 재시도하지 않는다. 중복 실행 가능성과 복구 방법을 확인한다.
- 시각·난수·I/O 의존성을 숨기지 않는다. 도메인 규칙은 DB나 웹 서버 없이 테스트할 수 있게 한다.
- 새로운 업무 규칙에는 정상 사례와 규칙 위반 사례를 검증하는 작은 테스트를 남긴다.

## 외부 계약·주석·로그

- 직렬화 포맷·스키마·공유 저장소 키를 바꾸기 전에 소비자를 확인하고, 필요한 호환성과 전환 방법을 명시한다.
- 직접 만드는 직렬화는 왕복 테스트로 검증한다. 잘못된 입력은 명시적으로 처리한다.
- 주석에는 코드로 드러나지 않는 업무 이유·외부 계약·기술 제약만 남긴다.
- 시크릿·접근 토큰·민감한 데이터를 코드나 로그에 남기지 않는다. 로그에는 확인된 사실과 필요한 오류 맥락을 기록한다.

공통 구현 원칙은 [Karpathy 스킬](../skills/karpathy-guidelines/SKILL.md)을 따른다.
